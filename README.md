# Kotai

Kotai is a macOS menu bar app that routes each model request to a personal or
work OpenRouter account. Cursor and other OpenAI-compatible clients can use both
accounts simultaneously through one stable URL.

## How it works

```text
Client model ID → ngrok → Kotai → routed OpenRouter account
```

- A `kotai/personal/` or `kotai/work/` model prefix selects the corresponding
  OpenRouter key for each request, so personal and work projects can run at the
  same time.
- Kotai strips the routing prefix before forwarding the real model ID to
  OpenRouter.
- Every model-bearing request must use an exact `kotai/personal/` or `kotai/work/` prefix.
- OpenRouter keys and the ngrok authtoken stay in the macOS Keychain.
- Clients authenticate with a separate proxy token generated by Kotai.
- Kotai listens only on `127.0.0.1:18742`; ngrok provides the public HTTPS URL.

## Requirements

- macOS 14 or newer
- Xcode 16 or newer
- A free [ngrok](https://ngrok.com/) account, its [authtoken](https://dashboard.ngrok.com/get-started/your-authtoken), and an assigned static dev URL from [ngrok Domains](https://dashboard.ngrok.com/domains)
- Two OpenRouter API keys

```bash
brew install ngrok xcodegen
xcodegen generate
./Scripts/reset-build-run.sh
```

On first launch, the setup wizard asks for:

- Personal and work OpenRouter keys
- Your [ngrok authtoken](https://dashboard.ngrok.com/get-started/your-authtoken)
- Your assigned static dev URL from [ngrok Domains](https://dashboard.ngrok.com/domains), such as `https://example.ngrok.app`
- A generated Kotai proxy token

Kotai stores credentials in the ordinary file-based macOS Keychain, matching the
Kehai/Sasu approach, as one JSON vault under the fresh service
`com.justin.Kotai.credentials.v3` with `AfterFirstUnlockThisDeviceOnly`
accessibility. On first access after upgrading, Kotai checks `v3` once, then checks
the legacy `com.justin.Kotai.credentials.v2` and `com.kotai.credentials` services
once each until it finds data. It copies the first complete decoded vault to `v3`
in one atomic write. A denied or cancelled Keychain request, or an invalid legacy
vault, stops migration and remains an access/error state rather than appearing as
missing setup. Legacy items are intentionally retained after a successful copy for
rollback safety; all subsequent reads and writes use `v3`.

The confirmed static ngrok URL is non-secret but travels in the complete vault so
migration and settings updates remain atomic. `UserDefaults` retains only the
non-secret last-known/legacy ngrok URL used as a setup suggestion; secrets are never
stored there. OpenRouter keys, the ngrok authtoken, and the Kotai proxy token remain
in Keychain. Kotai starts
ngrok with `--url` on every launch,
guaranteeing the same client base URL. Users upgrading from a version before static URL
configuration are prompted once, with their previously discovered URL prefilled for
confirmation.

## Client configuration

Use the generated proxy token as the client API key.

### Cursor

```text
https://example.ngrok.app/cursor/v1
```

In **Cursor Settings → Models → API Keys**:

1. Enable the OpenAI API key and paste the proxy token.
2. Enable **Override OpenAI Base URL** and paste the Cursor URL.
3. Add and select the desired prefixed model aliases described below.

### Model routing

Kotai routes each request according to its model ID. For example (model IDs are
illustrative; check OpenRouter for current availability):

- `kotai/personal/openai/gpt-5` selects the personal key, then Kotai sends
  `openai/gpt-5` to OpenRouter.
- `kotai/work/anthropic/claude-sonnet-4.5` selects the work key, then Kotai sends
  `anthropic/claude-sonnet-4.5` to OpenRouter.

Personal and work aliases can be active concurrently, allowing projects using
different accounts to run at the same time. Every model-bearing request must use
an exact `kotai/personal/` or `kotai/work/` prefix. Kotai strips only a recognized
routing prefix; unprefixed, case-mismatched, and malformed model IDs are rejected
rather than forwarded or silently routed.

The model-less `/models` endpoint remains a pass-through to OpenRouter and uses
the personal credential internally. It does not add Kotai aliases. Add each
desired `kotai/personal/<real-model-id>` or
`kotai/work/<real-model-id>` alias manually in Cursor or another custom client.

### Other OpenAI-compatible clients

```text
https://example.ngrok.app/v1
```

Use the generic URL with clients that support the OpenAI wire format and a
custom base URL. Anthropic-native clients are not supported.

## Notes

- Kotai, ngrok, and the Mac must be running for requests to work.
- Anyone with the proxy token can use either configured OpenRouter account
  according to model routing. Rotate it in Kotai and connected clients if exposed.
- Prompt data transits ngrok, Cursor when applicable, and OpenRouter.
- ngrok free-plan request and bandwidth limits apply.
- OpenRouter's Cursor integration is beta. Some Cursor features may bypass
  custom API keys or base URLs.

## Development

Kotai uses XcodeGen. `project.yml` is the source of truth and the checked-in
`Kotai.xcodeproj` is regenerated from it.

```bash
brew install xcodegen
xcodegen generate
xcodebuild -project Kotai.xcodeproj -scheme Kotai -configuration Debug \
  -derivedDataPath .build/DerivedData -destination 'platform=macOS,arch=arm64' \
  CODE_SIGNING_ALLOWED=NO build
xcodebuild -project Kotai.xcodeproj -scheme Kotai -configuration Debug \
  -derivedDataPath .build/TestDerivedData -destination 'platform=macOS,arch=arm64' \
  CODE_SIGNING_ALLOWED=NO test
```

For a signed local build that resets DerivedData and launches the app:

```bash
./Scripts/reset-build-run.sh
```

## Local releases

`project.yml` contains both release fields: `MARKETING_VERSION` is the semantic
version and `CURRENT_PROJECT_VERSION` is the monotonically increasing numeric
build. Update both and regenerate `Kotai.xcodeproj` with:

```bash
./Scripts/bump-version.sh 0.2.0
./Scripts/bump-version.sh 0.2.0 2
```

Copy `.env.release.example` to `.env.release` and set local credentials or
overrides. The defaults target `littlebobert/kotai`, sibling
`../littlebobert.github.io/kotai.html` and `kotai-appcast.xml`, Justin's Developer
ID team, and the `sasu-notary` keychain profile.

Sparkle 2.9.4 is configured by `project.yml`. Its public EdDSA key is embedded in
the app. The private key remains in the login Keychain under Sparkle account
`kotai`; release scripts pass that account to `generate_appcast`. The public feed
is `https://kotai.jp/kotai-appcast.xml` and its product link is
`https://kotai.jp/`.

For compatibility, `https://littlebobert.github.io/kotai-appcast.xml` remains
served for 0.1.0 clients. The next higher build bridges those clients to the
custom-domain feed.

Build and sign the arm64 application bundle with hardened runtime using the existing
Developer ID Application certificate for team `XDWKSAH7W3`:

```bash
./Scripts/build-release.sh
```

The ordinary macOS Keychain approach requires no provisioning profile, Keychain
Sharing access group, or application entitlement setup.

The app is produced at
`.build/ReleaseDerivedData/Build/Products/Release/Kotai.app`. Submit it for
notarization, staple the ticket, and create a ZIP plus SHA-256 checksum under
`.build/releases` with:

```bash
./Scripts/notarize-release.sh
```

Before publishing, preview the guarded release plan. Both repositories must be
clean and synchronized with their current upstream branches, and the landing
page must contain the documented download and changelog markers. Dry-run checks
version semantics, required tools, repositories, markers, notes, release
availability, and appcast paths without editing, building, translating,
notarizing, committing, pushing, or publishing.

```bash
./Scripts/deploy-github-release.sh 0.1.0 --dry-run --notes "Initial release"
```

Publish the prepared `0.1.0` release by passing the checked-in version explicitly.
This keeps the current `CURRENT_PROJECT_VERSION`. If the README download block
and landing page are already prepared, the workflow conditionally reuses those
commits rather than creating empty release commits:

```bash
./Scripts/deploy-github-release.sh 0.1.0 --notes "Initial release"
```

For the next patch release, omit the version or pass `--patch`. Both increment
the patch version and numeric build. A higher explicit semantic version also
increments the build; a lower explicit version is rejected.

```bash
./Scripts/deploy-github-release.sh --notes "Describe the change"
./Scripts/deploy-github-release.sh --patch --notes-file release-notes.md
```

A real deployment translates English notes to Japanese with OpenAI and falls
back to Anthropic when configured, updates the README and bilingual landing-page
marker blocks, regenerates `Kotai.xcodeproj`, builds and runs all Xcode tests,
builds and notarizes the app, and generates a Sparkle appcast. The appcast uses a
release-note sidecar, embeds those notes, emits no deltas, records the exact
numeric build, and points downloads at the GitHub release. The workflow stages
only its intended app and website files, conditionally commits changed files,
pushes, creates the GitHub release, then verifies the public artifact, landing
page, and appcast.

To publish an already-notarized `.build/releases/Kotai-<version>-mac.zip` with an
existing release-notes file, use the smaller workflow. It creates the GitHub
release and writes the sibling appcast, but leaves website commit and push to the
operator:

```bash
./Scripts/publish-release.sh
```
